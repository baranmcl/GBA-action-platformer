# Agent 2: Architecture & Design
**Date:** 2026-07-16 23:28
**Scope:** Maintainability + token-efficiency for adding dungeons/bosses/enemies

### [CRITICAL] play_room is an ~850-line god-function with open-coded entity handling; every new mechanic grows it linearly

**Evidence:** `src/game/scene_dungeon.cpp` — `play_room` defines 12+ ad-hoc instance structs (`EnemyInst`, `GateInst`, `BlockInst`, `BrazierInst`, `CrackedFloorInst`, `BoulderInst`, `LoosePlatformInst`, `HiddenPlatformInst`, `MagicCrystalInst`, `ShrineInst`, `HeartInst`, `TriggerInst`), each with its own inline spawn block, its own inline per-frame update/render block, and its own inline death-reset block, all interleaved in one function. The file's include list pulls in essentially every `logic/` and `engine/` header plus 20+ sprite items. The history is visible in the comments: M6 added cracked walls inline, M8 added four Stone blocks (pound resolution, loose platforms, boulders, heavy plates) inline, M10 added hidden platforms + crystals inline, M12–M14 added `run_room_boss` in the same TU.
**Problem:** There is no entity abstraction — "kind of thing in a room" is not a concept, so each kind is a struct + 3–5 hand-placed code blocks whose ordering constraints are documented only in comments ("MUST precede despawn_on_solid", "ORDER: gates -> braziers -> enemies…"). Adding one mechanic means finding the right insertion points in a 850-line loop with implicit inter-block ordering. This is the single biggest per-milestone code-growth driver and the most expensive file for an LLM to load and edit safely (its 1420 lines already exceed a comfortable single read).
**Risk:** Each future dungeon gimmick (D4–D8 bosses imply more mechanics) adds ~50–150 lines to the same function; ordering bugs between blocks (the water/ice-before-despawn class) multiply combinatorially; eventually no change to `play_room` can be verified without full regression QA of all 9 dungeons.

### [CRITICAL] The boss "framework" leaves two parallel ~350-line fight loops that require double-fixes, and BossDef is accreting per-boss flags with matching scene branches

**Evidence:** `run_boss` (`src/game/scene_boss.cpp`, 445 lines) and `run_room_boss` (`src/game/scene_dungeon.cpp:167–521`) are near-clones: both re-implement spell-icon refresh, clamped camera, ability sync, muzzle/aim, crystal respawn, `restart_fight`, `boss_say`, telegraph/Active/Recovery dispatch, and death/Game-Over flow. The Recovery-clear bug had to be fixed in both — the comment in `scene_boss.cpp` admits "the SAME fix already applied to the D1 room boss." Meanwhile `logic::BossDef` has grown one-off fields per boss: M13 added `locomotion` + `block_spell` + ROCKFALL, M14 added `expose_spell_alt` + `block_spell2`, each with a matching hand-written branch in `run_room_boss` (pacing block, dual-block block, `elem_base` 4-frame sprite math). Per-boss tuning is hardcoded in the shared loop: rock counts `(b.phase == 0) ? 3 : 5` and projectile speed `(b.phase == 0) ? 2 : 3` are D2's numbers applied to every future rockfall/aimed boss.
**Problem:** A "data-described" boss today actually touches ~6 code sites: `boss.h` (new `D*_DEF` + possibly new fields + `BossState` behavior), `boss_attacks.*` (if any new primitive), `run_room_boss` (branch for the new field), `build_level.py` `BOSS_SYMBOL`, `boss_sprite_for`, plus graphics. The flag-soup trend means boss #8 will carry ~10 mutually-interacting optional `BossDef` fields whose combinations (`TiredWindow` + `expose_spell_alt`? `Pacing` + rockfall leap offset?) are untested and mostly meaningless. The framework made boss #2–#3 cheaper than boss #1, but the marginal cost is rising again because per-boss behavior keeps landing in the shared loop instead of in data or in a per-boss strategy.
**Risk:** Five more bosses (D4–D8) at the current trajectory means `BossDef` becomes an unprincipled union of every boss's quirks, `run_room_boss` becomes a second `play_room`, and any change to the shared loop risks regressing three shipped fights that can only be verified by emulator QA.

### [MAJOR] Player/ability/HUD control is copy-pasted across three scenes (four sites) with no shared controller

**Evidence:** `refresh_spell_icon` lambda exists 4 times (scene_hub, scene_boss, twice in scene_dungeon); `set_clamped_cam` 4 times; the 5-line ability-sync block (`player.abilities.featherleap = world.has(...)` …) 4 times; the vine VFX + miss-vine animation (~70 lines) is duplicated verbatim between `scene_hub.cpp` and `scene_dungeon.cpp`; the crystal collect/respawn logic 3 times; the muzzle/aim computation 4 times. The project's own MEMORY.md lists "share player-ability controller" as a known deferred refactor.
**Problem:** These aren't incidental one-liners — the spell/grapple input branch (cycle → want_grapple → pull-block/pull-enemy/anchor → cast) is the game's core verb set, and it exists in three diverging variants (hub is "anchor-only", boss arena is "no blocks", dungeon is full). Any change to the control scheme (a new spell, the planned powers/controls menu, remapping) is a 3–4 site edit where the variants must be re-derived each time.
**Risk:** The variants drift (they already have: the enemy-pull exists only in `play_room`, so grappling an enemy works in a dungeon room but silently does nothing in a boss room with the same input), and each new scene type (D4–D8 boss variants, a possible mini-boss room) adds another copy.

### [MAJOR] Adding a dungeon requires mechanical, unvalidated edits across ~7 code/content sites

**Evidence:** For a new dungeon N today: (1) author `tools/levels/dungeonN_room*.txt` + `.json` per room; (2) hand-add includes + `DUNGEONN_ROOMS[]` + `DungeonData` to `include/game/levels/dungeons.h`; (3) extend the `if(n == …)` chain in `src/main.cpp`; (4) extend the `door_enterable` chain in `scene_hub.cpp` (which hand-encodes "door N needs spronk N−1" nine times instead of a formula); (5) add the door digit to the hub level txt (and digits stop at '9' — `build_level.py` parses `c in '123456789'`, so dungeon 10 cannot be expressed in the grid format at all); (6) write `test/test_dungeonN_level.cpp` by copying ~150 lines of static flood-fill helpers (the M14 plan *mandates* the copy to dodge ODR instead of extracting a shared test header); (7) if it has a boss: `boss.h`, `BOSS_SYMBOL`, `boss_sprite_for`, sprite assets.
**Problem:** The ASCII+JSON level pipeline itself is good, but everything around it is hand-wired with no manifest: `dungeons.h` room order, `main.cpp` routing, hub gating, and the single-character door namespace are all parallel structures that must agree by convention. The stated goal — cheap new dungeons — is bounded by these fixed costs, not by content authoring.
**Risk:** The '9' digit ceiling is a hard wall for the "expand existing dungeons / more dungeons" memory-noted goals; the copied test harness means a fix to the traversal model must be re-applied to 9 files; forgetting one chain edit produces a door that renders open but routes nowhere (`main.cpp` falls through on out-of-range n silently).

### [MAJOR] The level compiler validates almost nothing the runtime assumes; failures are silent truncation or OOB reads on hardware

**Evidence:** `play_room` clamps every spawn list to hard caps (`&& i < 8` for enemies/blocks/boulders/loose/hidden/crystals, `< 16` plates/buttons/braziers/cracked floors, `< 24` gates, `< 4` shrines/hearts — 15 such clamps), but `tools/build_level.py` never checks these caps: a 9th enemy in a .txt is silently dropped at runtime. `RoomDoorSpawn::target_room`/`target_entrance` are raw ints indexed into `dungeon.rooms[]` with no bounds check in `run_dungeon` and no cross-room validation in the compiler (each room compiles independently; there is no dungeon-level manifest); a typo'd `target_room: 3` in a 3-room dungeon is an OOB pointer dereference on GBA. `find_entrance` silently falls back to the '@' spawn on a missing entrance id. Latch IDs are hand-assigned small ints in scattered JSON sidecars (`dungeon6_room1.json: latch_id 0`, `dungeon7_room1.json: 1`, `dungeon8_room1.json: 2`) against a global 24-bit budget with no uniqueness registry — a collision silently pre-opens a shortcut in a different dungeon.
**Problem:** The pipeline's whole value is catching content errors at build time; it checks rectangularity and solid borders but none of the invariants that actually bite (caps, room-graph integrity, latch uniqueness, door digits). The per-dungeon C++ test files partially compensate, but only for invariants someone remembered to hand-copy.
**Risk:** At 12 dungeons with 30+ rooms, a content edit that trips any of these produces a hardware-only, hard-to-bisect failure (or a silent cross-dungeon save corruption via latch collision) — exactly the class of bug the three-layer/host-test architecture was built to prevent.

### [MAJOR] Global save bit-budgets are nearly exhausted and hard-shaped around "exactly 8 dungeons"

**Evidence:** `include/logic/world_state.h` — `latches` is one `uint32_t`: bits 0–23 for all shortcut latches game-wide, bits 24–31 for exactly 8 heart containers. `spronks_freed` assumes d ∈ 1..8 throughout (`door_enterable`, `spronk_count(w) == 8` for the finale door). `run_room_boss` defeat state is deliberately not persisted (comment: "the boss is NOT persisted; no save change"), so re-entering an arena room while backtracking re-triggers a mandatory full boss fight.
**Problem:** The stated direction is D3–D8 bosses plus richer multi-room retrofits of D1–D5 (MEMORY.md). Richer rooms mean more latched shortcuts; 24 bits across 12 dungeons is 2 per dungeon. Heart containers cap at 8 forever. Any expansion of these means a v6 save layout + a sixth migration branch in the already 5-branch `load_save`.
**Risk:** The bit budget becomes the design constraint ("can't add a shortcut, out of latches"), or a rushed save-layout change breaks the migration chain; the unpersisted boss-defeat state makes the planned dungeon retrofits (backtracking for heart containers through arena rooms) actively hostile.

### [MAJOR] The tile-index registry is a comment; visual/collision indices are re-pinned by hand at each use site

**Evidence:** The canonical tile map lives in a comment block in `include/logic/gates.h` (lines 30–35). `scene_dungeon.cpp` hardcodes bg indices at point of use: door archways 5/6/26 (with the comment "13 is lava, so 26 is the next free strip slot — see make_placeholder_art.py"), braziers 14/15, cracked floor via `gate_info(...).bg_tile` in one place but literal `11` semantics in another, `WATER_BG = 16, ICE_PLATFORM_BG = 19` pinned locally "(gates.h tile map)". Collision values are similarly split between `build_level.py`'s `TILE` dict, `logic/tilemap.h`'s `TileKind`, and casts like `(int)logic::TileKind::IcePlatform` at use sites.
**Problem:** Three artifacts (Python compiler, logic enum, art generator) plus N scene call-sites must agree on the same integers, with agreement maintained by grep and comments. Allocating "the next free strip slot" by reading a comment is exactly the manual process that fails once the placeholder art is replaced with real tilesets.
**Risk:** The inevitable art pass (placeholder → real tiles) requires re-deriving every pinned index across four files; a missed one renders the wrong tile with no build error, only visual QA.

### [MINOR] Boss/enemy visuals are bound by pointer-comparison and implicit frame-index conventions

**Evidence:** `boss_sprite_for` in `scene_dungeon.cpp` maps `BossDef*` → sprite via `if(def == &logic::D2_DEF)…` pointer identity; enemy art is a hardcoded ternary (`fire_immune ? fire_enemy : enemy`); boss sprite semantics are positional frame conventions (frame 0 normal, 1 exposed, 2–3 alt-element) enforced only by comments and the `elem_base` arithmetic in `run_room_boss`.
**Problem:** The three-layer rule (logic can't name `bn::` items) makes some game-side mapping necessary, but pointer-compare against def symbols is the most brittle possible key — a `BossDef` copied or defined in another TU silently falls through to the guardian sprite. A string/enum id on `BossDef` with one table in game/ would make the mapping data. Enemy variety is worse: "enemy type" isn't a concept at all (one patrol `Enemy` + one bool), so a genuinely new enemy means editing `logic/enemy.*` and three inline blocks in `play_room`.
**Risk:** Five more bosses extend the pointer-compare chain and the frame-convention special cases; the first dungeon that wants a second enemy behavior discovers there is no seam for it.

### [MINOR] Vestigial and misleading structure left behind by the milestone process

**Evidence:** `include/logic/dungeon1.h` contains only the fully generic `try_free_spronk` used by every dungeon — the name is a lie that costs a wrong first guess on every navigation. In `play_room`, `bool boss_defeated = false; if(level.boss != nullptr && !boss_defeated)` — the flag is dead (checked once, immediately after initialization). In `scene_boss.cpp`, the King ignores `BossDef.phases[].attacks` entirely (`KING_ATTACK_CYCLE` is hardcoded, with a comment conceding it merely "reproduces" the mask) — so the M12 claim that the King "reads the def" is only true for HP/phases/timers, and editing `KING_PHASES[].attacks` silently does nothing.
**Problem:** Each item is small, but the King's decorative attack mask is a plan-vs-reality divergence: the framework's flagship "data-driven" field is non-functional for its original consumer, which will mislead whoever tunes the King or clones its pattern for a D4–D8 boss.
**Risk:** Tuning-by-data edits that appear to work (compile, tests green) but change nothing at runtime; navigation friction compounds across a codebase whose primary consumer is token-budgeted LLM sessions.
